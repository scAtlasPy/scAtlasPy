# Atlas Data Model

scAtlasPy stores atlas-scale single-cell data in a persistent, DuckDB-backed
database with the `.sasql` file extension.

An Atlas is not simply an AnnData or Seurat object saved in another format.
It uses a database-oriented data model designed to support:

- persistent storage of complete atlases and analysis results;
- multiple expression representations without overwriting the original data;
- efficient sparse aggregation and cell-wise data retrieval;
- stable alignment of cells, genes, embeddings, and analysis outputs;
- bounded-memory queries, streaming computation, and minibatch access.

This page explains the main tables inside an Atlas and how they relate to
familiar concepts in AnnData and SeuratObject.

```{important}
The tables described here explain the current scAtlasPy data model. Unless a
table or field is explicitly documented as a public integration interface,
external packages should use the public `Atlas`, `sap.io`, query, streaming,
and minibatch APIs.
```

## Data Model at a Glance

The following table starts from the scAtlasPy representation and shows the
closest corresponding structures in AnnData and SeuratObject.

| scAtlasPy Atlas | Purpose | AnnData | SeuratObject |
|---|---|---|---|
| `obs` | Cell-level metadata | `adata.obs` | `meta.data` |
| `var` | Gene-level metadata | `adata.var` | Feature metadata in an assay |
| `X_HyS_data` and `X_HyS_indptr` | Sparse expression matrix and derived expression fields | `adata.X` and `adata.layers` | Assay layers such as counts, normalized data, and scaled data |
| `obsm_X_pca` | Cell-level PCA coordinates | `adata.obsm["X_pca"]` | PCA `DimReduc` cell embeddings |
| `obsm_X_umap` | Cell-level UMAP coordinates | `adata.obsm["X_umap"]` | UMAP `DimReduc` cell embeddings |
| `varm_PCs` | Gene loadings for PCA | `adata.varm["PCs"]` | PCA `DimReduc` feature loadings |
| `uns_pca_stats` | PCA summary statistics | `adata.uns["pca"]` | Information associated with the dimensional reduction or miscellaneous metadata |

These correspondences are conceptual rather than exact. scAtlasPy stores each
component as one or more database tables so that it can be queried and processed
without loading the complete dataset into memory.

## Persistent Cell and Gene Identity

The data model is organized around two persistent identifiers:

```text
atlas_cell_id
atlas_gene_id
```

These identifiers connect metadata, expression values, embeddings, loadings,
and analysis results across Atlas tables.

### Cell Metadata: `obs`

The `obs` table contains one row for each cell.

Common columns include:

- `atlas_cell_id`: the persistent cell identifier generated by scAtlasPy;
- `atlas_cell_name`: the original cell name, usually obtained from the source
  dataset;
- sample, donor, batch, condition, tissue, and other imported metadata;
- quality-control metrics and filtering flags;
- cluster labels, cell-type annotations, and model predictions.

For example:

```text
obs
├── atlas_cell_id
├── atlas_cell_name
├── sample
├── donor
├── condition
├── filter_cells
├── kmeans
└── cell_type_manual
```

Cell names may be duplicated across datasets, particularly when several studies
use similar barcode formats. Use `atlas_cell_id` whenever cell-level results
must be aligned unambiguously with the Atlas.

### Gene Metadata: `var`

The `var` table contains one row for each gene.

Common columns include:

- `atlas_gene_id`: the persistent gene identifier generated by scAtlasPy;
- `atlas_gene_name`: the original gene or feature name;
- imported gene metadata;
- gene-level quality-control statistics;
- filtering and highly variable gene flags;
- means, variances, and scaling-related statistics.

For example:

```text
var
├── atlas_gene_id
├── atlas_gene_name
├── gene_total_counts
├── n_cells_by_counts
├── filter_genes
├── highly_variable_genes
└── zero_scale_transform
```

Use `atlas_gene_id` when gene names are duplicated or when gene-level outputs
must be returned from another method.

## Hybrid Sparse Expression Storage

The expression matrix is represented by two core tables:

```text
X_HyS_data
X_HyS_indptr
```

Together, they form the hybrid sparse storage layer used by scAtlasPy.

### `X_HyS_data`

`X_HyS_data` stores coordinate-style sparse expression records. Each stored
record is associated with a cell and a gene:

```text
atlas_cell_id
atlas_gene_id
data
```

Only sparse records are stored directly. Expression values that are implicitly
zero do not require separate table rows.

### `X_HyS_indptr`

`X_HyS_indptr` stores row-pointer information for cells. It allows scAtlasPy to
locate the expression records belonging to selected cells efficiently when
reconstructing data blocks and minibatches.

The two tables provide complementary access patterns:

- `X_HyS_data` supports database queries and expression aggregation;
- `X_HyS_indptr` supports efficient cell-wise retrieval and matrix
  reconstruction.

This hybrid design underlies both Atlas queries and high-throughput expression
streaming.

## Multiple Expression Representations

Preprocessing functions can add new expression fields to `X_HyS_data` without
overwriting the imported values.

Common fields include:

| Expression field | Meaning |
|---|---|
| `data` | Expression values stored during import |
| `data_normalize` | Library-size-normalized expression |
| `data_log1p` | Log-transformed normalized expression, usually `ln(1 + x)` |
| `data_scale` | Centered and standardized expression |
| `data_sqrt` | Square-root-transformed expression |

For example, one sparse record may contain several representations:

```text
atlas_cell_id | atlas_gene_id | data | data_normalize | data_log1p | data_scale
```

This allows raw or count-scale values, normalized values, and transformed
values to coexist in the same Atlas.

The appropriate field depends on the downstream analysis:

- count-based models may require `data`;
- exploratory analysis and marker visualization commonly use `data_log1p`;
- PCA or model training may use `data_log1p` or `data_scale`, depending on
  whether genes should retain variance-dependent weighting or be standardized.

The selected expression field becomes part of an analysis view:

```python
atlas.build_read_index(
    cell_condition="filter_cells",
    gene_condition="filter_genes",
    use_hvg=True,
    use_data="data_log1p",
)
```

## Scaled Values and Implicit Zeros

Sparse storage normally omits expression values equal to zero. Before scaling,
an omitted entry can therefore be reconstructed as zero.

After gene-wise centering and standardization, an original zero becomes:

```text
(0 - gene_mean) / gene_std
```

This transformed value is usually not zero.

scAtlasPy stores the transformed value of an original zero in:

```text
var.zero_scale_transform
```

When reconstructing a dense batch from `data_scale`, scAtlasPy can therefore:

1. initialize each gene with its corresponding transformed-zero value;
2. insert the explicitly stored scaled expression records;
3. return a dense matrix consistent with gene-wise scaling.

Without `zero_scale_transform`, omitted sparse entries would be incorrectly
reconstructed as zero after scaling.

## Cell Embeddings

Cell-level multidimensional results are stored in `obsm_*` tables.

Common examples include:

```text
obsm_X_pca
obsm_X_umap
```

Each table contains `atlas_cell_id` together with the embedding coordinates:

```text
obsm_X_pca
├── atlas_cell_id
├── PC1
├── PC2
└── ...
```

The persistent identifier connects every embedding row to the corresponding
cell in `obs`.

## Gene Loadings

Gene-level multidimensional results are stored in `varm_*` tables.

For example:

```text
varm_PCs
```

contains PCA feature loadings associated with `atlas_gene_id`.

This separates gene-level model outputs from the gene metadata stored in `var`
while preserving identifier-based alignment.

## Analysis Statistics

Compact analysis metadata and statistics that do not belong naturally in
`obs`, `var`, `obsm_*`, or `varm_*` are stored in `uns_*` tables.

For example:

```text
uns_pca_stats
```

may contain PCA explained variance, explained variance ratios, and related
summary information.

The structure of each `uns_*` table depends on the analysis that created it.

## Relationships Between Core Tables

The main relationships in an Atlas can be summarized as:

```text
obs.atlas_cell_id
    ├── X_HyS_data.atlas_cell_id
    ├── X_HyS_indptr.atlas_cell_id
    └── obsm_*.atlas_cell_id

var.atlas_gene_id
    ├── X_HyS_data.atlas_gene_id
    └── varm_*.atlas_gene_id
```

These relationships allow cells and genes to be filtered, reordered, queried,
or processed in subsets without losing alignment between data components.

## Filtering and Analysis Views

scAtlasPy normally records filtering decisions as metadata rather than
immediately deleting the underlying expression records.

Common filtering columns are:

```text
obs.filter_cells
var.filter_genes
```

A read index combines these filtering results with a selected expression field
and, optionally, highly variable gene selection:

```python
atlas.build_read_index(
    cell_condition="filter_cells",
    gene_condition="filter_genes",
    use_hvg=True,
    use_data="data_log1p",
)
```

The resulting read index defines:

- the cells included in subsequent computation;
- the genes included in subsequent computation;
- the selected expression representation;
- the feature order supplied to downstream methods.

```{note}
A read index is an access view over the persistent Atlas. It does not create
another complete copy of the expression matrix.
```

## Inspecting an Atlas

Use the public inspection interfaces to examine the data model:

```python
atlas.table_names()
atlas.table_info("obs")
atlas.head("obs")
atlas.workflow_state()
atlas.read_index_info()
```

Compact metadata summaries can be retrieved with:

```python
atlas.query("""
    SELECT
        cell_type_manual,
        COUNT(*) AS n_cells
    FROM obs
    GROUP BY cell_type_manual
    ORDER BY n_cells DESC
""")
```

Direct access to internal tables is useful for understanding and developing
scAtlasPy, but user-facing workflows and third-party integrations should prefer
documented public interfaces.
